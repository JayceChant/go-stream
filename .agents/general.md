# 通用协作规范（项目无关、语言无关）

> 本文件为**跨项目复用**的语言无关协作规范，由各项目根目录的 `AGENTS.md` 引用生效；开始任何工作前先完整阅读。
> 与具体编程语言相关的规范（命名细节、工具链、质量门槛命令等）见同目录下的语言规范文件（如 [`go.md`](./go.md)）。

## 1. 规格文档（.spec/）

- 项目以 `.spec/` 维护规格文档：`.spec/README.md` 索引与全局约定（组织方式、EARS/ADR 边界；非规范）；`.spec/requirements.md` 行为契约（EARS：可观测行为、跨边界契约、业务规则）；`.spec/decisions.md` 决策记录（ADR：背景、备选方案与否决理由、后果；不作为实现依据）；`.spec/tasks.md` 任务清单（未勾选 = 待执行的前瞻任务，spec 改动中即可规划写入；勾选 = 已执行并通过验收）；`.spec/checklist.md` 固定验收动作清单（每次任务收尾须按序核对执行的例行检查，有序列表，不勾选）。根级位置即全局作用域；小型单域项目不建域子目录，拆分触发条件见 `.spec/README.md`。
- **spec 驱动开发循环**：行为类变更一律执行「讨论 → 写入 `.spec/tasks.md` → 确认 → 修改代码 → checklist 验收 → 勾选 tasks」；spec 改动先于代码落地。行为类变更的提交/PR SHALL 同批携带对应的 spec 文件（requirements/decisions）改动，使语义分歧在合入前暴露；纯 spec 的变更可先行独立合入，把语义对齐提前到编码之前（收尾核对见 checklist 第 2～3 条）。
- **需求收敛门禁（循环「讨论」步的固定产出）**：行为类变更在写入 spec 前 SHALL 先完成需求收敛并经用户放行，四要素缺一不可：核心对象（本轮到底在改什么）、In/Out Scope（做什么、明确不做什么）、成功信号（做完长什么样，给出可核对判据）、关键未知（尚无答案的问题，逐条标注是否阻塞起草）。门禁未过不得进入方案起草与代码实现——代理已自行开写时应被打断重回收敛；关键未知不阻塞时可放行，但对应口径须在 spec 中显式标注 `待实证：<触发事件或条件>`，实证后销账。收敛结论随 `.spec/tasks.md` 改动落账（决策依据/任务条目），不另建过程文件。
- **防假定稿**：讨论暴露需求盲区时，代理 SHALL 提问交用户裁决、结论落为「决策依据」，不得以自身假设填补盲区后直接起草。用户明示「想清楚了，直接开始」可跳过追问，但已指认的盲区仍须登记。
- **外部需求文档并入**：外部规格/需求文档不直接作为实现依据，SHALL 先做行为主张抽取与冲突检查（对照 requirements 既有条目与 decisions 的已否决/已取代方案，防复活），冲突项显式列出待用户裁决；确认后融入 requirements/decisions/tasks，原文不长期留存（参考资料保留外部链接）。本项目不设固定暂存目录，确需暂存时使用不入库的临时位置。
- 实现以 `.spec/requirements.md` 为准，任务范围以 `.spec/tasks.md` 为准，验收动作以 `.spec/checklist.md` 为准。
- 实现与 spec 冲突时，先修订 spec 并获得确认，再实现；不得绕过 spec 私自变更行为。
- 任务完成时勾选 `.spec/tasks.md` 对应项（先勾选后提交，见第 8 节），并按 `.spec/checklist.md` 核对全部验收动作；纯 spec 变更同样按 checklist 收尾。

## 1.1 精简纪律（`.spec/` 目录保持最小可用）

`.spec/` 目录的价值密度优先于历史完整性（完整历史在 git）：

- 各规格文件（`README.md`、`requirements.md`、`decisions.md`）目标长度均 **≤300 行**。超出时：只保留关键内容与最近条目；较久远且对后续开发影响不大、特别是已完成事项的展开描述（长篇 Scenario、已关闭的开放问题等）高度精简（一段话或删除）；删除内容由 git 历史留痕。**决策史不删**：被取代的关键决策写入 `decisions.md`（触发门槛见下），而非另设降级档案。新增 Requirement 前先评估是否可并入既有条目；文件持续膨胀时按 `.spec/README.md` 的拆分触发条件处理，而非放宽行数约束。
- `tasks.md` 仅保留：未完成任务、最近完成的任务、虽久远但对项目长远有影响的任务；已完成且无后续参考意义的批次条目直接删除（git 历史留痕），其中属于决策史的部分压缩为 ADR 条目。
- `checklist.md` 始终按当前实际需要执行的验收动态调整：过时验收项删除，新增有用验收项加入，不为历史保留条目。
- **EARS 与 ADR 的边界**：`requirements.md` 只写可观测契约（调用方/用户可观察的行为与反馈、跨边界契约、业务规则），判据是**删除测试**——删掉所有实现名词后条款仍能被 QA/集成方判定真伪；技术选型、内部组件与函数复用、文件与模块组织、构建与生成工具配置一律落 `decisions.md` 或代码注释/`docs/`。requirements 的「决策依据」只留一句当前理由 + decisions 指针；decisions 的「关联」指回 Requirement 标题。库项目的公开 API 名称/签名/返回语义属于跨边界契约，可留在 requirements；内部类型与实现机制不进入条款。
- `decisions.md` 是决策记录（ADR）：条目按日期倒序排列（新条目置顶），记录决策时背景、备选方案与否决理由、后果；**不作为实现依据**（现行口径以 requirements 为准）。触发门槛（清单制）：有真实备选且取舍非显然 / 用户裁决过需求盲区 / 跨领域或基础性选择（选型、目录结构、治理机制、CI 结构）/ 回退成本高 / 被否决方案值得后人知道（防复活）；普通功能不写。已采纳条目的方向变化写新条目并标注取代关系，口径微调追加「修订记录」，不得静默改写既有结论。
- **契约与演进分离**：spec 条目只载行为契约、判定口径与关键陷阱结论；实现演进过程、事故排查经过、函数/参数级实现细节一律不入正文——由 git 历史、代码注释、`decisions.md` 或 `docs/design.md` 承载。实现载体外置时只记「调用契约 + 指针」，不复制其内部口径。流程类内容（CI/构建/发版等）从紧：机制细节挂配置文件注释，spec 保持最小契约集。
- **精简动作随当次任务提交，不必单独立任务。**

## 2. Git 提交规范（强制）

- **每次被用户接受的修改，必须立即做一次 git commit**，不得积压多任务后混合提交。
- message 采用**中文 Conventional Commits** 格式：

  ```
  <type>(<scope>): <中文简述>

  <正文：动机与要点，可选>
  ```

  - `type`：feat / fix / docs / style / refactor / test / chore / perf / build / ci
  - `scope` 可选，取项目模块名；常用值见各项目 `AGENTS.md`
  - 示例：`feat(<scope>): 实现 Map/Filter 无状态算子`、`docs(spec): 修订错误处理模型`
- 一次提交只做一件事；只 `git add` 与本任务相关的文件，**不得** 将用户未提交的无关改动混入。
- 中文 message：按第 3 节在 Git Bash 中执行时可直接 `git commit -m "中文"`（UTF-8 全链路，已实测验证）；**回退**到 PowerShell/cmd 时，必须将 message 写入 **UTF-8 文件**并用 `git commit -F <file>` 提交，提交后用 `git log` 验证无乱码。临时 message 文件用后即删。
- `git merge` 统一使用 `--no-ff -m "<message>"`：`--no-ff` 保留分支合并拓扑；`-m` 显式给出 merge message（沿用 `Merge branch '<分支名>'` 风格）。禁止不带 `-m` 的 merge——未配置编辑器的终端（EDITOR/core.editor 缺失）会弹出 vi 编辑 `MERGE_MSG`，阻塞非交互命令执行。
- **主 type 以变更的影响面为准，CI/流水线相关提交一律 `ci`**：凡只触及 CI/CD 配置与脚本（`.github/workflows/`、构建/发布脚本、Dockerfile 构建链、部署脚本等）、与项目功能无关联的提交，无论 CI 内部性质是新增还是修复，主 type 用 `ci`（可副 `feat`/`fix` 修饰，如 `ci(fix):`），不得用 `feat`/`fix`。判断口径：终端用户只关心可用的功能——若该提交的受益者是开发者/流水线本身，就是 `ci`。已合入主线的提交不作追溯。
- **Git 身份卫生**：提交使用本人身份，代理在会话首次提交前 SHALL 核对 `git config --show-origin --get user.name` 与 `git config --show-origin --get user.email`，发现测试/平台机器人等非本人身份先恢复（unset 污染作用域、回落本人配置）再提交。测试确需伪造身份时 SHALL 将作用域限定在单次命令——`git -c user.name=… -c user.email=… <command>` 或 `GIT_AUTHOR_*`/`GIT_COMMITTER_*` 环境变量——禁止写入 `--local`/`--global`/`--system` 任何持久作用域；脚本沙箱验证优先使用独立临时仓库（用完即删）。
- 本仓库默认走「feature 分支 + PR 合入 master」流程，代理在独立分支上工作时遵循同一提交纪律；未经用户明确要求，不得执行 push、reset、force 等破坏性或外发操作。
- 提交内容不得包含本地路径（见第 7 节）、密钥、临时文件。

## 3. 命令执行环境（Shell 优先级，强制）

所有命令行操作（git、语言工具链、脚本等）统一遵守以下执行环境规则，以提高兼容性（中文/UTF-8/POSIX 工具链）：

- **本地环境路径等配置统一存放于项目根目录的 `.env.local`**（见第 7 节），执行命令前先读取，避免每次重复探测。
- **Linux / macOS**：无需特殊处理，使用默认 shell 直接执行。
- **Windows**：按以下优先级选择执行环境，仅当高优先级不可用时才降级：
  1. **WSL**（首选）：Linux 原生 bash 与 git（UTF-8 全链路，中文安全）；工具链经 interop 调用 Windows 侧可执行文件（如 `go.exe`，版本要求见语言规范文件）。项目路径形如 `/mnt/<盘符>/...`。
     - 注意：`C:\windows\system32\bash.exe` 即 WSL bash；勿与 Git Bash 混淆。
  2. **Git Bash**（次选）：完整 POSIX 工具链，中文安全。项目路径形如 `/d/...`。
  3. **cmd / PowerShell**（末选，仅当上述两者均不支持时）：例如需要 PowerShell 专属 cmdlet / `.ps1` 脚本、Windows 特有工具、COM/WMI 交互等场景。此时警惕中文编码问题（控制台默认 GBK 代码页），涉及中文输出/参数的操作参考第 2 节的文件中转方案。

## 4. 语言与文档

- 所有文档（spec / README / docs）与代码注释使用**中文**。
- 代码标识符（类型、函数、变量）使用英文，遵循所选语言的官方命名惯例（细节见语言规范文件）。
- **运行时报错文案使用英文**：panic/异常消息、库自身构造的 error 字符串等用户直接阅读的运行时输出，与标识符同属代码的对外门面——开源项目面向国际用户，不得使用中文；测试代码（含断言消息）例外。
- 新增或变更公开 API，必须同步更新对应文档；涉及用户可见行为时同步更新 `README.md` 与 `docs/api.md`。

## 5. 质量门槛总则（强制）

- **每次代码修改后、提交前，必须完整通过项目约定的质量检查**（具体命令清单见语言规范文件，如 [`go.md`](./go.md) 第 3 节），任一失败不得提交。
- 新功能必须带单测；修复 bug 先写复现用例再修复。

## 6. 每次循环的标准流程

1. 读 `.spec/tasks.md`，选择下一个未完成任务（遵循 Task Dependencies 顺序）
2. 阅读 spec 中相关章节，实现 + 单元测试
3. 勾选 `.spec/tasks.md` 对应项；按序核对 `.spec/checklist.md` 验收动作
4. 通过质量门槛（总则见第 5 节，命令清单见语言规范文件）
5. 等待用户接受
6. 按第 2 节 Git 提交规范提交（中文 Conventional Commits）
7. 回到第 1 步

## 7. 环境中立与其它全局规则

- **本地路径不得进入任何提交文档**（AGENTS.md、.agents/、.spec/、README、docs 等）：文档中只允许出现相对项目根目录的路径与本机无关的通用描述。本机绝对路径（shell 位置、项目根、工具链路径等）**只能**写入项目根目录的 `.env.local`。
- **`.env.local` 为本地环境配置 dotfile**：
  - 已在 `.gitignore` 中忽略，**禁止提交**；
  - 键值格式（`KEY=VALUE`），至少包含：`WIN_PROJECT_ROOT`、`WSL_BASH`/`WSL_PROJECT_ROOT`/`WSL_GIT`、`GIT_BASH`/`GIT_BASH_PROJECT_ROOT`，以及语言工具链路径键（Go 项目为 `WSL_GO`/`WSL_GOFMT`）；
  - 文件不存在时：按第 3 节优先级**现场探测一次**并生成，后续循环直接读取，避免重复探测。
- **不得回滚用户的手动修改**：工作区可能包含与当前任务无关的用户改动，保持原样、不带入提交。
- 不过度设计：不实现 spec 未要求的功能（非目标清单见各项目 `.spec/requirements.md`）。
- 提交信息、文档、注释中不得包含无根据的承诺（如未做的优化、未测的性能数据）。

## 8. 清单勾选纪律

- 任务清单（`.spec/tasks.md`）的勾选——含「执行提交」这类自指项——必须**先勾选、后提交**，纳入同一次提交；严禁提交后再补勾选。固定验收动作（`.spec/checklist.md`）为有序核对项，不勾选，但须逐条执行后方可提交。
- 每轮任务结束前执行 `git status --short` 确认工作区干净；有未提交改动时按第 2 节补提交或向用户说明遗留原因。
- 「做完了」的可验证判定（收口）：checklist 全条核对通过 + tasks 对应项先勾选后提交，二者齐备才算收口，不得凭执行印象宣告完成；相关文档回写（README/AGENTS/ADR 落账）与状态标记随同次提交落账。
